AgentCore Migration Lab / Tier 3 Migration

Tier 3 — From Bedrock Agents Classic to AgentCore

Now bring an existing agent across. You'll map each piece of a Classic configuration onto its AgentCore equivalent, then decide harness or code and wire up tools, memory and observability.

What "maintenance mode" means for you

Amazon Bedrock Agents — launched November 2023 — is now Bedrock Agents Classic. As of July 30, 2026 it is closed to new customers and in maintenance mode. Existing agents keep working; your Bedrock models, Knowledge Bases and Guardrails are unaffected. AWS recommends migrating Classic workloads to AgentCore.

Exam framing

"Maintenance mode + closed to new customers" ≠ "shut down." If a question implies existing Classic agents stop running, that's the distractor. Your Knowledge Bases and Guardrails are reusable assets, not casualties of the migration.

Map the configuration

Before deploying anything, take the Classic agent's configuration apart and line each element up against its AgentCore counterpart.

Bedrock Agents ClassicAgentCore equivalent
Foundation model + prompt instructionsModel + system prompt (harness config, or your agent code)
Action groups (Lambda-backed functions)Tools added via agentcore add tool
Knowledge BasesKnowledge bases attached to the agent (Classic KBs are reusable)
Prompt overrides / advanced promptsPrompt configuration on the harness, or logic in code
Session / conversation memoryAgentCore Memory
CloudWatch tracesAgentCore Observability (OpenTelemetry)
Primer: the import shortcut

You don't have to map everything by hand. The AgentCore CLI can import an existing Bedrock Agents Classic configuration as a starting point for either the harness or a code-based agent. Import-Agent tooling can also migrate Classic agents into LangGraph or Strands while wiring in AgentCore primitives like Memory, Code Interpreter and Gateway.

Even with import, understanding the manual mapping matters — the exam tests the mapping, and import gives you a starting point you still have to review.

Choose your path

Use the managed harness unless you have a specific reason to own the loop. A reason to go code-based: you already have an agent codebase to migrate, or you need orchestration the harness doesn't yet express. For a straightforward Classic agent — model, a few action groups, a knowledge base — the harness is usually the cleaner target.

Do it

Step 1 · Review the Classic agent

List its model, action groups, knowledge bases and prompt overrides. Each becomes a harness parameter or a tool. Write them down before you touch the CLI.

Step 2 · Scaffold the target (harness path)
agentcore create
# choose the managed harness, set model + prompt from the Classic agent
Step 3 · Add tools for each action group

Where Classic used Lambda-backed action groups, add AgentCore tools. Built-in tools cover common needs:

agentcore add tool --harness my-research-agent \
  --type agentcore_browser --name browser

agentcore add tool --harness my-research-agent \
  --type agentcore_code_interpreter --name code-interpreter

Custom action-group logic maps to your own tools rather than these built-ins.

Step 4 · Attach memory and knowledge, then deploy

Add AgentCore Memory where the Classic agent relied on session memory, and attach your (reusable) knowledge bases. Then apply everything:

agentcore deploy

Remember from Tier 2: add changes only take effect in AWS after a deploy.

Step 5 · Verify behaviour parity
agentcore invoke "<a prompt the Classic agent handled>" --stream

Compare the response and the tool calls against the Classic agent's behaviour. Check traces in CloudWatch (Observability) to confirm the tools fired as expected.
